# InterviewPath job data vs SpeakCV practice: what exists, what crosses

Scope: read-only. Facts only, with file:line. No recommendations.
Paths: `IP/` = `interviewpath/interviewpath-demo/`, `SC/` = `SpeakCV/src/backend/`, `SCF/` = `SpeakCV/src/frontend/`.

## Architecture reality (read first)

- No separate InterviewPath backend in this workspace. HR portal `IP/` (Vite) calls the SpeakCV FastAPI backend `SC/` (`IP/src/lib/api.js:3`, `IP/e2e/start-backend.sh:4-5` runs `SpeakCV/src/backend`).
- One DB, one `users` table, one `/api/login` for HR and candidates. HR is `company_members` rows (`SC/app/database/sql_models.py:284-296`).
- Two frontends on one backend: candidate app `SCF/` (Next.js), HR portal `IP/`.
- Consequence: "crossing over" is mostly a same-DB question, not an integration question. Cross-app link is only a URL with a token.

## 1. Job / request / application model

| Concept | Table / class | Fields for title, company, JD | Ref |
|---|---|---|---|
| Hiring request (HR intake) | `hiring_requests` / `HiringRequest` | `title` (String 255), `job_id` (FK, nullable). No JD text | `SC/app/database/models_bridges.py:19-33`, title `:25` |
| Job draft (AI JD studio) | `job_drafts` / `JobDraft` | `title` (nullable), `lines` JSON `{"text":{en,vi,ko}}`, `requirement_lines`, `job_id`, `hiring_request_id` | `models_bridges.py:35-55`, lines `:44`, title `:50` |
| Job (published posting) | `jobs` / `Job` | `title` (255), `slug` (unique, set at publish), `description` (Text, ONE language), `status`, `interview_languages`, `department_id`, `role_node_id`, interview window | `SC/app/database/models_hiring.py:18-39`, title `:25`, slug `:26`, description `:27` |
| Requirements | `job_requirements` / `JobRequirement` | `text`, `must_have`, `visibility` (public/internal/confidential), `active`, `position` | `models_hiring.py:42-53` |
| Application | `applications` / `Application` | `job_id`, `job_version`, `candidate_user_id` (FK users), `alias` ("#A1"), `source_channel` (channel NAME), `cv_text_blind`, `stage`, `hr_decision` | `models_hiring.py:69-105`; `candidate_user_id` `:77`, alias `:78`, source_channel `:79`, stage `:86` |
| Company name | `companies` / `Company` | `name`, `slug`, `default_locale`, `is_sample` | `SC/app/database/sql_models.py:254-259` |

Facts:
- No "position" column distinct from `title`. No company name on Job or Application: join via `company_id`.
- Application has no job slug, no JD, no requirement text.
- Job.description language = company default locale: `SC/app/bridges/publishing.py:233` (`_description(draft, lang)`), `:164-165`; `default_language` at `SC/app/bridges/publishing.py:65-67`.
- Title precedence: request title wins over draft title (`SC/app/bridges/jd_studio.py:312-317`); new job title from it at `publishing.py:187-189`.
- Publish flow: HiringRequest -> JobDraft (approved) -> `publishing.publish` `publishing.py:211-262` creates/updates Job, sets `draft.job_id` `:246`, `request.job_id` `:250`. Slug built in `SC/app/hiring/jobs.py:180-197` (`:189-193`).
- `JobDraft`/`HiringRequest` are HR-only; candidate never sees them.

## 2. Candidate "next step" link: construction and params

### Link-out (InterviewPath -> SpeakCV job page)
- Backend builder: `SC/app/bridges/channels.py:71-76`: `f"{public_url()}/jobs/{job.slug}?src={link.token}"`. Base = env `SPEAKCV_PUBLIC_URL`, default `http://localhost:3000` (`channels.py:22`, `:71-72`). Used for channel copy at `channels.py:188` and `:206`.
- Portal builder: `IP/src/lib/jobs.js:6` (`SPEAKCV_URL` from `VITE_SPEAKCV_URL`), `:14` (`channelUrl = ${SPEAKCV_URL}/jobs/${slug}?src=${token}`). Rendered in `IP/src/components/ChannelLinks.jsx:17` (clipboard), `:52` (display). Used on job editor `IP/src/routes/JobEditorPage.jsx:414`.
- Two env vars, same meaning: `SPEAKCV_PUBLIC_URL` (backend) and `VITE_SPEAKCV_URL` (portal). Prod compose wires backend from frontend var: `docker-compose.prod.yml:79`. Dev defaults both `localhost:3000` (`.env.example:10`, `:62`).
- Query params: ONLY `src` = `JobChannelLink.token` (`models_hiring.py:56-66`, token `:64`, generated by `secrets.token_urlsafe(16)` at `SC/app/hiring/jobs.py:206`). No job id, title, company, JD, or candidate identity.
- `src` use on SpeakCV side:
  - Click counter only: `SC/app/routers/public_jobs.py:23-30` (unknown token ignored).
  - Channel label stored: `SC/app/hiring/applications.py:54-58` `_channel()` -> `Application.source_channel` (`models_hiring.py:79`). Token itself not stored on Application.

### Candidate click path in SpeakCV (where the user clicks)
1. `SCF/app/jobs/[slug]/page.tsx:137` reads `src` from URL; `:146` `getPublicJob(slug, src)`.
2. Candidate logs in (`loginHref()` at `:180`), uploads CV: `:82` `applyToJob(slug, file, consent.version, consent.language, src)`.
3. `SCF/services/hiring.ts:146` -> `POST /api/public/jobs/{slug}/apply` (`SC/app/routers/applications.py:203-224`, auth required via `get_authenticated_user` `:205-211`).
4. Redirect `SCF/app/jobs/[slug]/page.tsx:83` -> `/applications/{id}/fit`.
5. Fit page: `SCF/app/applications/[id]/fit/page.tsx:154-159`: "practice first" link `/interview?next=${encodeURIComponent("/applications/${id}/screening")}`. Rendered ONLY when `LEGACY_B2C` (`:154`).
   - `LEGACY_B2C` = env `NEXT_PUBLIC_LEGACY_B2C_ENABLED === "true"` (`SCF/lib/features.ts:1`).
   - `/interview` layout calls `notFound()` if flag off (`SCF/app/interview/layout.tsx:3-6`).
   - Default false: `docker-compose.yml:31`, `.env.example:6`.
6. Practice `?next=` is only a return link: `SCF/app/interview/page.tsx:85-86` (`nextHref`), rendered `:376-378`. Not job data.

### InterviewPath -> SpeakCV practice
- No link to `/interview` or any practice route anywhere in `IP/src` (grep: none).
- Only SpeakCV-side link to practice is #5 above.

## 3. Candidate identity

- `users` (`SC/app/database/sql_models.py:10-22`): `email` unique (`:14`), `full_name` (`:15`), `hashed_password`, `role`. Same table for HR, candidates, admins.
- Application -> user: `candidate_user_id` FK (`models_hiring.py:77`). Apply requires a logged-in SpeakCV user (`routers/applications.py:205-211`), so every real application has a user row with email.
- Email match is therefore possible in-DB (`users.email`), but a logged-in candidate already maps to their applications by user id: `GET /api/me/applications` (`routers/applications.py:227-231`).
- HR-side identity is masked: `SC/app/hiring/board.py:159-161` (`_candidate_terms`), `:164-169` (`identity_masked` unless revealed). Name/email leave via `SC/app/hiring/decisions.py:145-154` (`reveal`, audit-logged). Candidate email shown to HR only after reveal.
- Candidate contact email exposed to candidate only once approved: `routers/applications.py:134-138` (`contact_email`).

Auth:
- Same login for both apps: `SC/app/routers/auth.py:37-55` (`POST /api/login`), JWT HS256 with `sub=email` (`SC/app/auth/security.py:14`, `:28-34`). Dependency `SC/app/auth/dependencies.py:21-25`.
- Token storage is per-origin, per-app:
  - SpeakCV: `sessionStorage["token"]` (`SCF/services/api.ts:12`).
  - Portal: `sessionStorage["portal_token"]` (`IP/src/lib/api.js:4`).
- No SSO, no cross-app token handoff, no API key between apps, no webhook, no HMAC between apps. Only shared secret is `SECRET_KEY` used internally for reapply guard (`SC/app/hiring/reapply_guard.py:19`).
- Google OAuth is a separate login path (`routers/auth.py:78`).

| `GET /api/applications/{id}/fit` | `:257-271` | `{requirements:[{requirement_id,text,fit}], team_style:[...]}` |

## 5. E2E fixtures (realistic shape)

Harness: `IP/e2e/start-backend.sh` runs SpeakCV backend on SQLite, creates companies via `app.cli create-company --name ...` (e.g., "Board Sample Company"), then seed scripts. Fixtures write ORM rows directly, bypassing the apply endpoint.

- `IP/e2e/seed_board.py`:
  - `seed()` `:174-176`: job "Sample Platform Engineer", `description="Sample job for tests"` (placeholder, not real JD). Requirements `:177-185` incl. one `visibility="confidential"`.

- `IP/e2e/seed_feedback.py`:
  - `make_job()` `:21-30`: realistic-ish description "Run FastAPI services with Docker in production.", two must-have requirements.
  - `make_application()` `:32-42`: user `sample-feedback-{n}@example.test`, `full_name="Sample Person {alias}"`, `stage="ready_for_hr"`, `cv_text_blind` from `CV` constant `:17`. Note: `make_application` takes `job` as argument; the job's title/description are the only job context.
- `IP/e2e/seed_insights.py`:
  - `make_job()` `:17-27`: description "Sample job for tests", three requirements (one `must=False`).

- `IP/e2e/seed_onboarding.py:22-26` `make_user()`: real password hash (`get_password_hash(PASSWORD)`), unlike `"!"` in board/feedback seeds.
- Realism summary: titles are real-looking; descriptions are mostly placeholders; candidate CV is a 1-2 line blind text; no seed sets a real JD body or company description.

## Summary of what exists (facts)

- Job title, company name, JD text (one language), requirements: exist in `jobs` / `companies` / `job_requirements`. Reachable by candidate only via (a) their application (title + company, no JD) or (b) public slug endpoint (JD + requirements, slug needed).
- Application to job: `applications.job_id`. Candidate to application: `candidate_user_id`. No slug on application response.
- Link-out carries only `src=<channel token>`. Nothing about job/position/company/JD crosses on the link.
- SpeakCV practice Setup (`SCF/components/Interview/SetupForm.tsx`) fields position/company/jd live in in-memory React state (`SCF/hooks/useInterviewState.ts:24-30`), no URL or storage prefill. Position auto-fills only from master-CV title (`SCF/app/interview/page.tsx:136-143`). Prompt built from them at `SCF/hooks/useInterviewActions.ts:267-269`.
- Today: zero job context flows from InterviewPath to the SpeakCV practice tool.
